大家好，我是 AI 超元域。

把一个 AI 助手交给自己使用，与让整个团队共同使用，遇到的问题很不一样。多人登录后，谁能看到对话和文件？私人记忆会不会进入公共项目？工具调用和凭据应该由谁管理？这期我在本地部署 qm，重点检查这些基础协作流程。

本文整理自 2026 年 8 月 3 日的视频简介、章节和对应的已保存校正字幕。此次未取得 YouTube 在线字幕导出，文章记录当时的实测，不代表重新部署或完成了一轮安全审计。文中“隔离”首先指演示中的作用域和可见性表现，不承诺任何部署都绝对安全。

## qm 面向的是多人共享 Agent 的问题

[01:15 的介绍](https://www.youtube.com/watch?v=TBVjqvueeCo&t=75s)将 qm 放在团队使用场景中：大家可以共享 AI 能力，同时保留各自的私人空间。

[官方仓库](https://github.com/yc-software/qm)在 2026 年 10 月 24 日核对时，将项目描述为面向工作的多人 Agent Harness，并明确区分个人与共享作用域。记忆、文件、权限、Keychain 视图以及持久化沙箱等资源，都围绕作用域组织。

这里的 Keychain 视图不能简单理解为“每个人都能读取所有原始密钥”，共享项目也不意味着自动共享所有个人资料。部署时需要理解具体授权和配置，而不能只看界面上有没有一个“私有”标签。

本期没有进行对抗攻击、越权访问测试或基础设施审计。因此，“适合团队协作”是功能定位，“已经达到某项企业安全认证”则是本文没有验证的另一类结论。

## 本地部署后的两个入口：管理与使用

[04:08](https://www.youtube.com/watch?v=TBVjqvueeCo&t=248s)从管理员控制台开始，随后进入普通用户的 Web UI。管理界面用于查看和管理用户等内容，日常对话则在用户界面中进行。

这样的分工很重要：聊天体验只是整个系统的一部分，团队还需要身份、配置和权限的管理入口。本期后续新增第二个账号时，就回到管理员面板确认用户已出现，再进入项目完成邀请。

视频讨论了 Pi Agent、Codex、OpenCode 和 Claude Code 等接入方向；实际对话演示使用的是 Pi Agent。不能把讲解中的兼容选项写成四种后端都逐一完成过实测。当前支持方式和配置细节应以对应版本文档为准。

## 记忆测试：记录习惯之后还能查看和修改

[06:05 的记忆演示](https://www.youtube.com/watch?v=TBVjqvueeCo&t=365s)，我告诉 Agent 自己通常使用 Claude Code 写代码，再用 Codex 做 review。

运行过程显示它读取并更新记忆，随后在记忆界面中可以找到这条开发工作流。还可以查看历史记录、直接修改内容、切换视图或删除条目。

这个过程的价值在于记忆是可以检查的。用户能看到系统记下了什么，也能纠正它。对于团队工具，记忆不仅要“记得住”，还要有合适的归属和维护方式。

本期说明了记忆写入与管理界面，并没有验证所有记忆在任意版本、任何异常重启后都保持一致。长期运行和数据恢复仍需单独测试。

## 创建共享项目：让第二个用户加入同一段工作

[07:15](https://www.youtube.com/watch?v=TBVjqvueeCo&t=435s)创建名为“AI 研究”的项目，并邀请另一个账号加入。

测试先注册第二个用户，通过邮箱登录。随后在原账号的项目中添加该用户并保存。第二个账号刷新后，可以看到这个共享项目。

接着，第二个用户在项目中提问“大模型微调时如何防止过拟合”。切回原账号，可以看到这段对话，并接着要求讲解第一条内容。再次切换到第二个用户，刷新后也能看到后续问答。

这一段把团队协作最基础的闭环跑通了：同一个项目、不同账号、共享对话、接续提问。它适合团队共同研究问题，而不需要每个人把回答复制到别处再转发。

## 私人空间与共享空间：本期看到的边界

[08:38](https://www.youtube.com/watch?v=TBVjqvueeCo&t=518s)继续比较私人内容和项目内容的可见性。通过普通界面切换账号时，没有看到对方的个人私有对话；加入共同项目后，则可以看到项目中的交流。

需要准确限定这个结果：它验证的是当时两个账号在应用界面中的访问表现，不代表系统管理员、数据库管理员或服务器所有者在所有层面都无法接触数据，也不等于证明不存在越权漏洞。

如果准备投入团队使用，应该为自己的配置补充验收：移出项目后是否失去访问权限，文件链接是否遵循项目权限，日志和备份有哪些人能读，以及模型服务会收到哪些内容。这些是建议检查的项目，不是本期已经跑过的测试。

## 共享文件：成员能看到过程，但不夸大分析结果

[10:10 的演示](https://www.youtube.com/watch?v=TBVjqvueeCo&t=610s)向共享项目上传文件，并让 Agent 分析内容。切换账号后，另一位成员可以看到相关对话，界面显示工具调用和运行过程，文件侧栏也能找到上传的文件。

当时演示中 PDF 分析尚在进行，没有立即输出结果。因此，这一段支持文件与任务过程在项目内可见，不能写成“PDF 已完整分析且结论准确”。

这是协作工具验收时容易忽略的区别：文件能共享、任务能启动、结果能产出、结果正确，分别需要证据。不要因为前两步顺利，就把后两步也一并视为通过。

## 执行流程与部署建议

[11:47](https://www.youtube.com/watch?v=TBVjqvueeCo&t=707s)解释了整体流程：消息由 Web UI 或 Slack 进入核心，根据身份和来源识别作用域，再由配置的 Harness 与模型处理；需要工具时，经过相应策略与执行环境，结果返回后继续判断，最后回复并保存有关记录。

本文不会由“有记录、有审计”进一步推导出模型自动训练更新，或者所有操作都经过独立安全验证。持久化与审计能帮助追踪过程，其覆盖范围和保护效果仍依赖具体实现和部署。

想复现本期环境，可以参考我的[从零安装笔记](https://github.com/win4r/mytest/blob/main/qm.md)。笔记明确区分本地测试环境与生产部署，不能把本地 HTTP 配置直接暴露到公网。正式部署前还应核对最新[官方项目文档](https://github.com/yc-software/qm)，并处理身份验证、访问范围、备份、凭据和网络入口。

这期最明确的收获，是 qm 把私人工作与团队协作放进了同一个使用流程：记忆可以管理，共享项目可以连续讨论，文件和执行过程可以被成员看到。下一步真正值得投入的工作，是围绕团队自己的权限边界做验收，而不只是把一个聊天界面部署起来。
